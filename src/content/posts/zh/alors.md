写代码的项目里，总有一批命令是要反复敲的：

- 安装或更新依赖
- 构建项目
- 构建 release 版本，或者构建调试版本
- 以 release 模式运行
- 以 debug 模式运行
- 跑测试，一遍又一遍
- 切换 profile
- 部署
- 跑 CI/CD 里的某一步
- 生成一些图表

它们来自不同的工具，而且这批命令本身会随着项目演进不断变化。

错位出在心智模型上。我们脑子里想的是「要做一件事」——测试、部署、运行、构建；
手上敲的却是「用哪个工具去做这件事」。这层对应关系本身并不常变，但每次跨过它，
都要付一次小小的上下文切换：这一步又该用哪个工具来着？

这个问题已经有工具解决了一部分。我自己就干过：在我做的第一个 C/C++ 项目里，
还没换到 CMake 之前，我们用 GNU make 做的不只是定义构建流程 —— 还写了一个
`clean` target 去删掉中间产物。那时候的 make 其实算不上 C 的构建工具，它是个
快捷命令的入口。

我们真正想要的，是一个代表项目本身去执行的东西：把所有可能用到的命令收在一处，
让人不必再记住背后是哪个工具，只留下意图。像 `my_project run`、`my_project dev`、
`my_project deploy` 这样。这才顺着人的思维走。

更专门的工具也有。npm 允许我们在 `package.json` 里定义临时的快捷命令，但它绑定在
JavaScript 生态里。`just` 只做这一件事，而且做得不错：`just run`、`just dev`、
`just deploy`，日常用起来很顺手。

但随着我的用法变复杂，它的一些设计开始不合用了：子命令，以及如何导入另一个
justfile、好让项目不至于只剩一个又长又大的文件。在它的设计里，这两个概念多少被
揉在了一起。

于是，在 AI agent 的帮助下，我做了 `alors`。目的相同，思路受 just 启发，但把子命令
和文件导入重新设计成了两件独立的事。shell 命令的执行方式上也有细微差别，更偏向
显式和严格 —— 在 AI agent 已经和我们一起写命令、跑命令的今天，我觉得这一点比以往
更重要。
